### 🤖 Assistant · 2026-07-31T02:16:51.745Z

I've read issue #36 and grounded it in the actual pipeline (`build_cli.py` walks a per-unit manifest, gating/repairing/stamping each unit independently). Here's my honest assessment.

## Short version

The **engineering design is genuinely good** — careful, defensive, preserves every invariant. But the **premise deserves scrutiny before you build it**, and the sequencing is backwards relative to #35. I'd call it a "yes, but not yet, and confirm the motivation first."

## What's strong about it

- **Failure isolation is right.** Per-unit parse/gate/stamp/persist, retry only failed units, deterministic fallback ladder to pack-size-1, per-unit repair scoping. This correctly refuses to let one bad sibling poison a clean one — which is the thing that usually kills batch-generation schemes.
- **It's gated, not gambled.** Default `pack_size: 1`, opt-in, and it refuses to flip the default without evaluator + human-review parity. That's the correct posture for anything touching content quality, and it respects the "human review is the gate" invariant you already learned ([[standalone-builder-done]]).
- **Invariants preserved explicitly** — WCF-1, citation tags, D1–D8 anti-padding, draft-only. The issue author clearly knows this codebase.

## Where I'd push back

**1. Interrogate the actual benefit before building.** The issue's own non-goals admit the tell: *"fewer calls ≠ proportionally lower token-metered usage."* Packing only saves the **deduplicated shared preamble**, amortized over `pack_size`. Each unit's passage/brief/references and *all output tokens* are unchanged. So:
- If the bottleneck is **token metering** → savings ≈ (shared rubric size × (pack_size−1)). Bounded, possibly marginal. And **prompt caching** would capture most of it with *none* of the parsing/isolation complexity.
- If the bottleneck is **`claude -p` invocation allowance** (per-invocation subscription limits) → packing is the *right* lever, because caching doesn't reduce invocation count. This is the case the issue implicitly rests on ("repeated invocations … consume automation allowance quickly").

Those two lead to different solutions. Worth confirming which one is actually biting you — the whole cost/benefit hinges on it.

**2. It can't prove its own worth without #35.** The evaluation plan (D1–D8 mismatch, gate rates, human acceptance across pack sizes 1/2/4/hybrid) *requires* the experiment framework in #35. So #36's value is unmeasurable until #35 lands. Building #36 first means shipping an opt-in feature nobody can responsibly turn on. **#35 should clearly precede #36.**

**3. Complexity vs. surface.** Envelope parsing, ID reconciliation (missing/dupe/cross-unit), fallback ladder, resume semantics, per-unit repair inside a shared response — that's a lot of new failure modes for a *draft-only, prepare-time* optimization that's invisible to the end product. The test matrix (partial output, truncation, sibling isolation, resume) is correspondingly large. Justified only if the invocation-allowance pain is real and current.

**4. Quality dilution is subtler than failure isolation.** The design handles *invalid* siblings well, but the real risk is a *valid-but-blander* unit 4-of-4 from attention dilution — passes the deterministic gate, fails D1–D8 evaluator or human taste. The eval plan does cover this, which is good; just don't let "gate pass rate held" get mistaken for "quality held."

## My recommendation

Good idea, well-specified, **but reorder and de-risk**:
1. Confirm the bottleneck is **invocation count**, not tokens. If it's tokens, try prompt caching first — much cheaper.
2. Land **#35 first** so #36 is measurable on day one.
3. Then build #36 exactly as spec'd — the defensive design needs no changes.

Want me to check whether the shared draft preamble is actually large relative to per-unit inputs (which would tell us how much packing could even save), or look at whether `claude -p` invocation count vs. tokens is the real constraint?

## Read

- **If the bottleneck is `claude -p` invocation count** → packing is worth it regardless of these percentages: N=4 turns 4 calls into 1, full stop. The preamble size is irrelevant to that axis.

- `<slug>` = kebab-case, 2–5 words, naming the session's **overarching theme or
  outcome**, not just the last thing worked on. If the session covered several
  threads, name it for the dominant one, or use an umbrella term that covers them.

Representative-name examples:

| Session | ✅ Good slug | ❌ Weak slug |
|---|---|---|
| Designed + built two HS courses, wrote an alignment report | `shormann-hs-math-courses` | `fix-tests` (last step only) |
| Debugged a flaky CI job, then documented the fix | `flaky-ci-timeout-fix` | `session-2` (meaningless) |
| Several unrelated small fixes | `misc-cleanup-and-fixes` | `dark-mode` (one thread of many) |

## Common mistakes

- **Naming for the last task instead of the whole session.** The slug must capture
  the session's overall arc. Re-read the contract's examples.
- **Producing only one of the two files.** Both the summary and the transcript are
  required, and they must share the same `YYYY-MM-DD-<slug>` base name.
- **Hand-writing the transcript instead of running the script.** The verbatim log
  comes from `render_transcript.py`, not from you retyping the conversation.
- **Forgetting to create `docs/sessions/`**, or writing to `docs/` root instead.
- **Padding the summary with invented specifics.** If a commit SHA, test count, or
  file path isn't in your context, say so instead of fabricating it.
